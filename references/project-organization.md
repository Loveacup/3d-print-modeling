# 项目管理、文档与接续

建立、推进、接续、整理或交付项目时读取。既组织人和agent把目标做成，也使成果、决定和证据可继续使用；管理深度随项目规模调整，不为统一外观重建目录或任务层级。

## 项目管理接入与本地后备

**已有适用软件及skill时接续使用。** 先识别现有项目、责任和任务，不每次对话重建。需要Linear协作时读取当前可发现的`linear-flow`，再选其对应CLI/MCP/API；其他软件按各自能力接入。区分skill已发现、连接已可用、读取成功和远端写入授权，不因看见配置就声称已连接。

**没有可用接入时，在项目内建立管理。** 复用README、核心需求、项目状态或已有任务记录；必要时增加一个项目内任务/决策文件。按实际需要保留目标成果、负责者、优先级、依赖、阻塞、重要决定、验收证据和下一步，不固定文件名/字段配额，不默认开发管理软件。临时对话todo可帮助当轮执行，但不能代替跨会话的项目记录。

**分清信息正本。** 使用外部管理软件时，工作状态、责任和承诺以选定系统为准；核心需求、模型、图、切片工程和验证证据仍在所属项目，以链接关联。无外部系统时，项目内管理记录承担状态正本。单机路径不可供协作者访问就说明可达方式，不因链接工单自动上传私有资产；避免两边各维护一份互相冲突的状态。

**围绕成果推进。** 将可独立验收的工作分清，只有真实前置条件才建立依赖；准备就绪、已获准且无冲突的工作可并行。同一文件或模型确定写入责任；收到结果后核实际产物和验收依据，不以“已派发/进程结束”当完成。持续阻塞时，执行方及时交出准确输入、失败产物和错误；协调方读取证据并决定修正或换路，不让下游空等完整长报告，也不等用户催促才介入。阻塞、决定、验收或下一步实质变化时记录，不要求每条消息更新，不把组织工作交回用户。

**已有系统断联时不静默换正本。** 项目内记待同步的对象、变更与证据，继续不依赖远端的工作；恢复后核现有对象与先前回执，再合并并读回，避免重复建卡。长期迁移明确新正本及旧引用。权限或目标项目不明只阻塞相关远端动作，不阻塞独立准备。

**问题与经验另有回路。** 日常项目推进仍在选定管理方式；[每次使用闭环](closeout.md)把发现的问题关联GitHub Issues，并把经验写进可发现的skill知识。项目任务与改进issue相互链接，明确谁负责哪个状态，不制造同一承诺的双正本。产物完成与反馈未同步分别报告。

## 当前入口与资料分工

**存放位置统一在项目。** 需求、现场资料、研究、审核图、交付说明、最终Markdown/HTML/PDF及其本地附件，均在所属项目目录维护；跨项目通用参考放本工作区参考资料，技能维护沿用本工作区现有维护目录。此规则覆盖旧的Obsidian默认交付偏好，不再维护知识库正文副本。需要从知识库找回旧资料时，比对版本和内容，保留原文、来源路径/身份、附件与旧→新映射，再更新项目入口；历史副本不覆盖最新核心需求。迁入核验后知识库不保留正文副本或跳转占位，来源映射及后续更新只在项目目录维护。

**整理时检查旧位置。** 首次整理项目或发现资料散落外部时，检查Obsidian知识库（含`00-Inbox`收件箱）中本项目的正文和所引本地附件；区分独立项目资料与仅提及项目的混合笔记。核对项目内原文、附件及来源映射完整后，在当前授权与权限内移出旧位置的副本或占位，交付项目内入口，不另建跳转笔记。无新外部资料的小改不重复全库扫描；共享附件和无关笔记不随本次收敛擅自删除。

用户要求“全部收敛”或指出仍有遗漏时，先重新枚举当前实际知识库的文件（含收件箱、非Markdown附件和原候选外目录），结合文件名、正文/标签、项目路径和引用辨别归属；不能只按几个文件名前缀或旧迁移清单选文件后宣称全库完成。为候选保留处理/排除原因，正文、专用附件、共享附件及混合笔记分别判断；迁出后再次独立发现并核旧位置、附件与当前索引。明确核查的是哪一端/哪一个库；另一端或用户所见文件未定位时保留待核，不凭最近打开记录推断缓存/同步故障。日常小改仍不重复全库扫描。

每个项目必须有独立的`核心需求.md`，按[需求维护规则](requirements-and-review.md#核心需求文档每次调整前必读)管理。已有同用途独立文件可以沿用，由README明确指向唯一入口；其余内容可按规模放README或链接专门文件。

| 内容 | 至少保留什么 | 常见位置 |
| --- | --- | --- |
| 当前入口 | 当前阶段、各有效用途/分支的准确版本和路径、部件/数量、整体预览、已验证/待验证、下一步、负责会话与核查日期 | 项目README；工作区项目状态只留摘要与链接 |
| 核心需求 | 当前目标、必须满足项、取舍偏好、范围边界、关键待确认项及确认依据 | 独立核心需求.md；短而可直接执行 |
| 现场资料 | 原图与标注索引、尺寸/基准/来源、实物版本、观察与设计影响、待补项及纠正记录 | 有现场资料即维护独立现场资料.md或已有同用途文档；按[收到即整理](requirements-and-review.md#现场资料收到即整理)执行 |
| 依据与决策 | 详细方案比较和否决原因；需求/审核确认对应的版本；链接现场资料作为依据 | 文档或研究/版本；核心需求只链接细节 |
| 参考与基线 | 所有收到/采用的参考模型、原始包及必要配套文件，来源清单、用途、单位与原件身份 | 参考资料、原始基线；保持原件不变 |
| 审核与开发 | 对应阶段的意向/结构审核图与图源、用户标注、候选/批准范围；可编辑CAD/参数化源和重建依赖 | 审核草图、研究、工作文件/版本 |
| 交付与验证 | 最终网格/3MF、部件和硬件清单、装配/打印说明；几何、路径、实际切片报告，哈希/配置与限制，实物反馈 | 打印文件、交付或对应版本的报告 |
| 历史与复盘 | 旧版、弃用方案、旧确认、阶段快照、整理映射；可复用结构候选与结论 | 归档/日期或历史版本，可从当前入口追溯 |

当前入口按每种有效用途/变体分别给出一个明确入口；确需一组互补文件时，列清各文件角色和关系。多个有效分支写明适用对象及验证范围；尚待用户验证时明确指定入口与待验项，不并列近似“最终版”让用户猜。候选/失败版放工作或历史区域，结论被新反馈推翻时同步撤回当前入口与分支说明中的可用表述；用户总体“能打开”按原话和范围记录。交付链串起核心需求与批准图→源模型/CAD→网格→实际图→3MF→验证；已有核过的部件清单、实例变换与基准/净高数据时，图文和装配HTML共同引用或生成于该数据，改动基准后只重算受影响项。按既有结构归位，不为建立入口复制制造文件；仅移动/改名须核字节身份并更新引用，不算新切片。

## 轻量交付身份清单

交付、接续或复用验证时，按本轮需要把选定源/参数、导出、交付物、图和验证证据关联到准确路径与版本。已有README/清单能表达就沿用；需反复核字节或同名文件易混淆时，用[身份清单工具](../scripts/delivery_identity.py)生成独立JSON快照。不强制迁目录、不建全项目数据库、不自动扫描或改写模型，也不要求每个项目具备所有角色。只有网格的旧项目如实标明缺源，不能补造CAD或追认过去已验收。

**先选对象，再取身份。** 依据当前需求/用户确认及实际文件确定本轮集合，而非自动挑最新文件。每项记录稳定ID、角色、原路径、版本（未知写`unknown`）；必要时用`relates_to`关联其他条目ID，把导出/交付、参数/源、证据/被检对象串起。说明关系依据，如真实生成命令/工具版本、日志、明确用户确认或`未验证`；这些可留在关联的证据/决定文档，不另建依赖推断器。同一文件承担多个角色时可以用不同ID明确列出。证据正文仍应含方法/验证器版本、输入身份、条件、结论及限制，文件存在不能代替这些内容。

可选工具只用Python标准库。以下是**格式示例，不是项目事实或固定文件套数**；按实际选择写UTF-8 `selection.json`，相对路径以显式`--root`为基准，JSON中的Windows反斜杠须转义，也可用`/`。现有目录之外的已授权文件可用绝对路径，不必搬入项目。角色支持`source/parameters/export/delivery/evidence/image/decision/reference`；`version`可为`unknown`，`relates_to`可省略。不要向选择文件填写工具生成的`sha256/status`。

```json
{
  "revision": "R01",
  "entries": [
    {"id": "model", "role": "source", "path": "工作文件/模型.scad", "version": "R01"},
    {"id": "mesh", "role": "export", "path": "交付/模型.stl", "version": "R01", "relates_to": ["model"]},
    {"id": "check", "role": "evidence", "path": "验证/几何报告.json", "version": "R01", "relates_to": ["mesh"]}
  ]
}
```

从主skill目录执行（替换为实际根目录/选择/输出路径，带空格路径加引号）：

```powershell
python -B -X utf8 scripts/delivery_identity.py capture --root "C:/项目" --selection "C:/项目/selection.json" --manifest "C:/项目/identity-R01.json"
python -B -X utf8 scripts/delivery_identity.py verify --root "C:/项目" --selection "C:/项目/selection.json" --manifest "C:/项目/identity-R01.json"
```

`capture`只读明确选中的文件并独占创建新清单，**不覆盖**已有路径，不允许输出冒充缺失输入；已有清单要保留，真正改版时另取新路径。`verify`只向stdout报告，不写清单或模型，也不把当前哈希静默补作旧基线。选择文件应从当前独立入口核实，不为使检查通过而改清单/选择。文件在核查期间须无同写者；检测不是持续监控，也不是并发快照或防篡改签名。

| 身份结果 | 含义与处理 |
| --- | --- |
| `matched` 已匹配 | 本次可读文件与记录SHA256一致，且对应条目ID、角色、原路径、版本和关联未变；capture中的matched仅表示新取样成功，不是历史或制造验收 |
| `changed` 已变动 | 字节不同，或选择条目的路径/角色/版本/关联、集合发生变化；保留旧快照，只复核受影响依赖与证据，不自动更新基线 |
| `missing` 缺失 | 明确选择的路径当前不存在；记录缺口，不从其他目录找同名文件冒充 |
| `unverified` 未验证 | 缺少原始哈希，或文件不能读取/实际是目录；后补文件不会自动升级为匹配。清单自身缺失/无效则整次核查受阻，不称已匹配 |

返回码`0`是所有选定身份匹配（不是项目通过）；`1`表示已形成结果但有变动/缺失/未验证；`2`表示输入格式、清单或输出受阻/拒绝。capture返回`1`也可能已创建如实记录缺失项的清单。核`verify`顶层`context_matched`：根目录或修订变化会使其为false并返回`1`，即使各条目的字节仍相同。非法/空集合、重复ID、未知角色、坏哈希、悬空关联、`..`、盘符相对路径、设备名和数据流路径拒绝处理；不可读不等于不存在。运行输出失败可能留下未完成的新清单，须核退出码和完整JSON，不以文件存在当成功。

**哈希只证明所取文件字节身份，不能证明来源依赖、几何一致、物理性能或选图授权。** `relates_to`只是调用者声明，不证明源确实生成了导出，身份匹配也不代表报告结论正确/仍适用。几何继续按[独立读取](geometry-validation.md#独立读取最终结果)，制造按[交付类型](slicing-and-delivery.md#3mf交付类型与补格式)选择检查；清单不触发切片启动核查或控机。清单和关联记录可能含私人路径/来源，外发仍需授权。

## 参考模型全部有去处

盘点项目内模型、ZIP、附件、图纸与外部依赖，把每个来源包及其模型列入清单；同一包可按包登记并列出实际采用的成员/对象、原包与解包关系。未采用或未研究的参考也登记状态与用途，避免无从识别的散件。

清单记：本地路径、来源URL/作者或用户提供来源、可确认的版本/取得日期、许可信息（缺失写未知）、单位/缩放及其确认程度、角色（原件、接口基准、外形灵感、结构候选、弃用参考）、采用部位和派生文件；关键原件留哈希。资料少时可在README中列一张表，资料多时独立清单。

主动检索与下载交接按[参考研究](reference-research.md)，沿用这份清单登记；Dot返回路径不等于本地已收到，须由接收方核可读原文件与哈希。

原文件保留原样；修复、缩放或改名后的工作副本与原件关联。3MF源工程预设只代表源文件。照片/网页/视频记录定位信息和实际读取范围，用户标注关联版本；无法访问的来源记缺失，不冒充已归档或已审查。借鉴前检查工作原理、装拆、受力和制造条件。

按本轮任务实际打开采用的参考模型：外形灵感可看缩略图，判断接口、内部结构、尺寸或坡面时须读取对应实体/网格和实例变换。记录读到哪个成员及范围；源模型参数、缩略图比例与现场实测尺寸分别标注，不能相互替代。

## 整理与交接

1. **确定当前身份。** 先读核心需求、README、清单和最新确认，区分有效分支、原件、派生物与历史；不凭文件名或修改时间决定当前版。
2. **保留再移动。** 记录移动前路径、数量与关键文件哈希；批量搬迁保存逐文件清单/哈希。待改写的旧说明留快照，原始参考、旧批准与弃用方案保留。没有授权不删除历史。
3. **按内容归位。** 沿用既有目录补索引；确需移动时保留旧→新路径映射，更新当前文档链接、状态及输入引用。历史脚本保留旧路径时标明重建所需目录/依赖，不把它当当前可直接运行入口。
4. **核完整保留。** 每份原文件都有去处，未修改二进制哈希一致，新增/重写/移动分开记；核当前文档与归档入口链接、版本对应。有交付包时查成员与外部文件一致。仅数量相同不能证明全部保留。制造依据等需保持哈希的旧文档快照，保留原字节，另记原相对链接基准并提供可点击解析索引；将文件缺失与迁入后链接基准变化分开报告。
5. **交接准确入口。** 给当前成果与README的绝对路径、有效版本、未验证项及整理结果。共享状态写入前重读，仅合并本项目段；实质进度后更新，不要求每条消息写状态。

核对随实际整理范围执行；单改一段说明无需全盘重哈希。文档完整不替代[几何复核](geometry-validation.md)或[切片验证](slicing-and-delivery.md)。

共享文档局部合并时保留未负责章节的实际字节，写入后重新读取验证；仅比较写入前字符串不够。Windows自动换行会把已有CRLF再次转换成CRCRLF，采用明确换行方式或字节拼接。写入前核当前版本，按章节判断并保留其他会话的新内容；发现异常时只修复能够与原快照精确对应的旧段，当前有效段独立验收。

## 中间文件清理

只在用户明确的清理/整理范围内，按当前依赖与恢复方式而非文件名、年龄或大小判定。源码、原始参考/现场资料、当前交付、独一刀路和必要失败证据保留；共享运行环境、`.tmp/.lock`、缺源或用途不明内容保留或列明待判断。普通小改不扩成全工作区扫描，跨项目请求逐项目记录已检查和未改原因。

项目自建源码旁的Python字节码，核对应`.py`仍在且不属于依赖安装/共享运行时后可清；不必因通用Python进程一概停下，锁定或权限受阻则跳过。可再生成不代表缓存字节相同。独立G-code只有与留存3MF的明确内嵌成员SHA256完全相同，才可作为可精确恢复的冗余候选；不匹配的刀路不能靠将来重新切片替代。

历史报告提到路径不等于现行流程直接依赖：现行重建/审核脚本需要的路径保留；仅历史一次性诊断引用的重复副本，在保留原路径→容器/成员→哈希、提取方法及历史脚本恢复布局说明后可清。逐候选分类，无法判断则保留，不为增加清理量放宽标准。

清理前留当前交付身份、受改说明原字节和逐项动作依据；清理后核交付未变、保留来源仍可读、当前链接有效。删除独立G-code时逐项核留存成员哈希及依赖；本轮确实删除可从容器精确恢复的刀路时，按范围选代表项在临时位置实际提取、独占创建并拒绝覆盖已有文件，再清除验证副本；没有此类删除则不增加恢复演练。不以重切片冒充恢复。记录删除、移动、归档与保留，区分删除总量和新增清单后的净空间变化；详见[可恢复清理的边界](publication-notes.md#可恢复的中间文件清理)。

## 每个项目怎样回收结构

每次使用结束按[知识循环](closeout.md)回收相关问题与经验；结构类经验采用以下分工，不要求每次都有结构贡献。方案取舍或收尾时研究当前项目相关的连接、承托、活动、导流和打印拆分机制，结合最新使用反馈、弃用原因与实际证据，在项目复盘留候选和结论。多项目吸收任务记项目/已读来源/发现或无需新增/回填位置/待补证据，未读项目不算已吸收。

| 内容性质 | 回填位置 |
| --- | --- |
| 特定尺寸、配方、原模型、未解释现象和本次验证输出 | 原项目文档与记录，技能只链接 |
| 值得迁移的结构机制或参数化模块 | [项目结构库](project-patterns.md)：问题、工作方式、相比备选的收益、代价/失效方式、适用边界、证据等级与源路径；模块另指向可编辑源和必要参数，不复制整套模型进技能 |
| 有依据且能帮助同类选型的检查方法 | 合并到[对应结构卡](common-structures.md)，避免同义条目堆积 |
| 会改变通用工作顺序的教训 | 按[收尾流程](closeout.md)窄幅修正对应步骤并检验决策 |

先查已有内容，确有新增价值再收录；无新增则记理由。整体不好用时仍可提取局部机制，但必须保留反证。后续反馈变化就修正原条目；逐项目有依据地积累，不要求每个项目贡献一条通用规则。
